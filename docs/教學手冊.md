# OrderService 教學手冊

這份手冊說明目前這支服務怎麼分層、一筆請求怎麼走完、訂單狀態怎麼變、登入怎麼擋請求、建立之後的待辦怎麼被背景程式收掉，以及怎麼在終端機和 Swagger 頁面上自己看到這些變化。

## 先從哪裡讀

不要從資料夾名稱開始。沿著 `POST /orders` 走一次，四層怎麼接起來就會出現。

1. `src/OrderService.Api/Endpoints/OrderEndpoints.cs`  
   對外有哪些網址。
2. `src/OrderService.Application/Orders/CreateOrderCommand.cs`、`CreateOrderCommandValidator.cs`、`OrderDto.cs`、`OrderService.cs`  
   進來的形狀、輸入檢查、出去的形狀，以及中間怎麼編排。
3. `src/OrderService.Domain/Entities/Order.cs`  
   什麼叫一張合法訂單，狀態只能怎麼變。
4. `src/OrderService.Application/Common/Interfaces/IOrderRepository.cs`、`IOutbox.cs`  
   Application 向外面要的能力。
5. `src/OrderService.Infrastructure/Persistence/OrderRepository.cs`、`OutboxWriter.cs`、`Configurations/`、`AppDbContext.cs`  
   那些能力怎麼落到 PostgreSQL。
6. `src/OrderService.Api/Program.cs`，以及 Application、Infrastructure 各自的 `DependencyInjection.cs`  
   啟動時誰被註冊、例外怎麼變成 HTTP 狀態碼、驗證中介軟體排在哪裡。`src/OrderService.Infrastructure/Outbox/OutboxWorker.cs` 也在這裡被啟動。它透過 `OutboxDispatcher` 把待辦交給對應的 handler。
7. `src/OrderService.Api/Auth/`、`src/OrderService.Api/Endpoints/AuthEndpoints.cs`  
   登入、簽發 JWT，以及哪些路由要帶 token。
8. `src/OrderService.Api/OpenApi/OpenApiExtensions.cs`  
   開發環境的 OpenAPI 文件和 Swagger 頁面，以及文件上哪幾條路由要帶 token。

`src/OrderService.Infrastructure/Persistence/Migrations/` 裡的 Designer 和 `AppDbContextModelSnapshot.cs` 是 EF Core 產生的。要對表結構時再看 `InitialCreate.cs`、`AddOrderStatus.cs` 和 `AddOutboxMessages.cs` 即可。

## 四個專案

| 專案 | 負責 |
| --- | --- |
| `OrderService.Api` | HTTP。接收請求、回傳狀態碼、檢查 Bearer token。開發環境另外提供 OpenAPI 文件。不寫商業規則。 |
| `OrderService.Application` | 用例。建立、查詢、付款、取消的步驟。 |
| `OrderService.Domain` | 規則。訂單怎麼建立、狀態怎麼轉移。 |
| `OrderService.Infrastructure` | 技術細節。EF Core、PostgreSQL、repository 實作、密碼雜湊，以及 outbox 的寫入和背景輪詢。 |

依賴方向是 Api 使用 Application 和 Infrastructure，Application 使用 Domain，Infrastructure 使用 Application 與 Domain。Domain 不引用 EF Core，也不知道資料庫存在。

## 建立一張訂單

`POST /orders`，內容像這樣：

```json
{ "customerName": "Ada", "amount": 120 }
```

1. 這條路由標了 `RequireAuthorization()`。`UseAuthentication` 先檢查 `Authorization: Bearer ...`，`UseAuthorization` 再決定放不放行。沒有有效 token 時回 `401`，`OrderService.CreateAsync` 不會被呼叫。token 從哪來，寫在「登入」。
2. 通過之後，`OrderEndpoints` 把 JSON 綁成 `CreateOrderCommand`，並向容器要 `OrderService`。金額如果不是數字，綁定失敗，`Program.cs` 回 `400`，欄位錯誤是 `Amount must be a number.`。
3. `CreateOrderCommandValidator` 檢查欄位有沒有給：名稱空白、金額缺漏是輸入錯誤，回 `400` 的 `ValidationProblem`。
4. 輸入通過之後，`OrderService.CreateAsync` 才呼叫 `Order.Create`。名稱超過 200 字、金額小於或等於 0，是業務規則，丟 `DomainException`。通過之後訂單狀態是 `Draft`。
5. `OrderService` 先在同一個 `DbContext` 放一筆 outbox：類型 `OrderCreated`，內容是這張訂單的 id。接著透過 `IOrderRepository.AddAsync` 存檔。`AddAsync` 的那一次 `SaveChanges` 同時寫入 `orders` 和 `outbox_messages`，兩筆一起成功或一起失敗。
6. 端點回 `201`，body 只有 `{ "id": "..." }`。這時候背景程式不一定已經跑到這筆。訂單的 `owner_id` 是 token 裡的使用者 id。

查詢自己的訂單是 `GET /orders`，單筆是 `GET /orders/{id}`。兩條都要帶登入拿到的 token。回得來的是這個帳號建立的訂單；別人的 id 回 `404`。`OrderDto` 的 `status` 是字串：`Draft`、`Paid` 或 `Cancelled`。

修改草稿是 `PUT /orders/{id}`，body 和建立時相同。已付款或已取消的訂單不能改，回 `422`。刪除是 `DELETE /orders/{id}`，成功回 `204`。這兩條也只處理自己的訂單。

## 依賴注入在做什麼

`Application/DependencyInjection.cs` 只有一件事：告訴容器，有人要 `Orders.OrderService` 時，為這個 HTTP 請求建立一個。

```csharp
services.AddScoped<Orders.OrderService>();
```

`AddScoped` 表示同一個請求裡共用這一個實例，下一個請求再做一個新的。`Program.cs` 只呼叫 `AddApplication()`，所以之後多了別的應用服務，也是加在這個方法裡。

端點沒有自己 `new`。參數上寫了 `OrderAppService`，框架就去容器裡找。`OrderService` 的建構式還需要 `IOrderRepository` 和 `IOutbox`，兩個都是 `AddInfrastructure` 註冊的：

```csharp
services.AddScoped<IOrderRepository, OrderRepository>();
services.AddScoped<IOutbox, OutboxWriter>();
```

介面在 Application，實作在 Infrastructure。Application 因此不必引用資料庫套件。

`OrderEndpoints.cs` 開頭的這行，是因為命名空間和類別都叫 `OrderService`，這裡取別名才分得開：

```csharp
using OrderAppService = OrderService.Application.Orders.OrderService;
```

## 訂單狀態

新訂單一定是 `Draft`。轉移寫在 `Order.Pay()` 和 `Order.Cancel()`，外面不能直接改 `Status`。

| 現在 | 動作 | 結果 |
| --- | --- | --- |
| `Draft` | `Pay()` | `Paid` |
| `Draft` | `Cancel()` | `Cancelled` |
| `Paid` | `Pay()` | `DomainException`：Order is already paid. |
| `Paid` | `Cancel()` | `DomainException`：Only a draft order can be cancelled. |
| `Cancelled` | `Cancel()` | `DomainException`：Order is already cancelled. |
| `Cancelled` | `Pay()` | `DomainException`：Only a draft order can be paid. |

對應的網址：

- `POST /orders/{id}/pay`
- `POST /orders/{id}/cancel`

這兩條和建立、查詢、修改、刪除一樣標了 `RequireAuthorization()`，要帶登入拿到的 token。

找不到訂單時，Application 回 `null`，端點回 `404`。規則不允許時，例外往外拋，由 `Program.cs` 的 middleware 接住，回 `422` 的 `ProblemDetails`，`title` 是 `Business rule violated`，`detail` 是領域訊息。

付款和取消會先 `GetByIdAsync`，呼叫領域方法，再 `UpdateAsync` 存檔。規則仍留在 `Order`，Application 只負責把步驟串起來。成功時，`UpdateAsync` 前會在同一個 `DbContext` 放一筆 outbox：付款是 `OrderPaid`，取消是 `OrderCancelled`，內容都是訂單 id。`UpdateAsync` 的那一次 `SaveChanges` 同時寫入訂單狀態和這筆待辦。找不到、不是自己的訂單，或領域方法拒絕時，不會放這筆。

## 資料怎麼進 PostgreSQL

`docker-compose.yml` 啟動 Postgres 17，主機連接埠是 `5433`。API 用的連線字串在 `src/OrderService.Api/appsettings.json` 的 `ConnectionStrings:DefaultConnection`。

`OrderConfiguration` 決定表和欄位：表名 `orders`，欄位 `id`、`customer_name`、`amount`、`status`、`created_at_utc`。`status` 以字串儲存，既有資料的預設值是 `Draft`。

`outbox_messages` 記的是還沒做完的後續工作：`id`、`type`、`payload`、`created_at_utc`、`processed_at_utc`。建立訂單時 `processed_at_utc` 是空的。

API 啟動時，`Program.cs` 呼叫 `ApplyMigrationsAsync()`，把尚未套用的 migration 寫進資料庫。其中一次會建立 `users`，並讓 `orders.owner_id` 指向使用者。套用時會清掉還沒有主人的舊訂單和 outbox。`AppDbContextFactory` 只給 `dotnet ef` 產生 migration 時用，執行中的 API 不走那條連線字串。

## 註冊和登入

訂單的查詢、建立、修改、刪除、付款、取消都要先登入。`POST /register` 和 `POST /login` 本身保持公開。`POST /login` 若也要求 token，就沒有人拿得到第一張 token。

`POST /register` 把帳號寫進 `users`。名稱去掉前後空白後不能空、不能超過 64 字，而且不區分大小寫，`Ada` 和 `ada` 是同一個名稱。密碼至少 8 字、最多 128 字。密碼不會原樣進資料庫，存的是 PBKDF2 雜湊。名稱已有人用，回 `409`，`title` 是 `Username is already taken.`。成功回 `201`，body 是 `{ "id": "...", "username": "..." }`。

登入名稱和訂單上的 `customerName` 是兩件事：前者決定這個請求是誰，後者是訂單資料。伺服器留下的是雜湊和同一把 `SigningKey`。token 的 `sub` 是使用者 id。之後每個請求自己帶上 token，中介軟體用這把鑰匙驗簽名，端點再用 `sub` 找出這個帳號的訂單。

`Auth` 還有 `Issuer`、`Audience`、`TokenLifetimeMinutes`。`SigningKey` 至少 32 bytes，因為簽章演算法是 HMAC-SHA256。這把鑰匙只給本機練習；換一把鑰匙之後，舊 token 全部失效。

先註冊。下面用 `staff` / `practice`，這組帳號現在來自這次請求，不是設定檔：

```json
{ "username": "staff", "password": "practice" }
```

```bash
curl -i -X POST http://localhost:5064/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"staff","password":"practice"}'
```

名稱已存在會得到 `409`。密碼少於 8 字得到 `400`。

沿著 `POST /login` 看：

```json
{ "username": "staff", "password": "practice" }
```

1. `AuthEndpoints` 把 JSON 綁成 `LoginRequest`。名稱或密碼空白，回 `400` 的 `ValidationProblem`，和建立訂單的輸入錯同一種形狀。
2. 兩個欄位都有值，才和 `AuthOptions` 裡的帳號逐字比對。任一不符，回 `401`，`title` 是 `Invalid credentials`。回應不會指出是名稱錯還是密碼錯。
3. 通過之後，`JwtTokenIssuer` 簽一張 token。內容裡有 `sub`（使用者名稱）、`iss`、`aud`、`exp`，簽章時還會帶上 `iat` 和 `nbf`。有效時間是 `TokenLifetimeMinutes`，預設 60 分鐘。
4. 端點回 `200`：`{ "token": "...", "expiresAtUtc": "..." }`。

token 是三段用句點接起來的文字：標頭、內容、簽名。內容可以被讀出來，簽名保證它是這把 `SigningKey` 簽的，而且內容沒被改過。

帶 token 的請求長這樣：

```http
Authorization: Bearer 這裡換成token
```

`Program.cs` 裡，中介軟體的順序是：

1. 最外層仍是原本那個例外 middleware。`DomainException` 還是在端點裡被接住，變成 `422`。`401` 是驗證結果，不是例外，所以不會被它改寫。
2. `UseAuthentication`。方案是 JWT Bearer。它讀 `Authorization` 標頭，檢查簽名、`iss`、`aud`、以及 `exp`。`ClockSkew` 設成 0，過了 `expiresAtUtc` 就失效。
3. `UseAuthorization`。它看這條路由有沒有 `RequireAuthorization()`。有，而且上一步沒有建立有效身分，就回 `401`，回應標頭是 `WWW-Authenticate: Bearer`，端點方法不執行。
4. 最後才是 `MapAuthEndpoints` 和 `MapOrderEndpoints`。這兩行要排在兩個 `Use` 後面，驗證才看得到這次請求。

`Order`、`OrderService` 沒有出現使用者。誰可以呼叫 HTTP，是 Api 的事。

自己發一次：

```bash
curl -i -X POST http://localhost:5064/orders \
  -H 'Content-Type: application/json' \
  -d '{"customerName":"Ada","amount":120}'
```

沒有標頭，狀態是 `401`。

帳密不對：

```bash
curl -i -X POST http://localhost:5064/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"staff","password":"nope"}'
```

名稱空白：

```bash
curl -i -X POST http://localhost:5064/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"","password":"practice"}'
```

登入成功：

```bash
curl -i -X POST http://localhost:5064/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"staff","password":"practice"}'
```

把回應裡的 `token` 貼到「自己看一次狀態變化」的 `Authorization` 標頭，或貼進下一節 Swagger 頁面的 Authorize。下面的查詢、建立、修改、刪除、付款、取消，以及輸入錯、業務規則錯的那些請求，都要帶這張 token；沒帶的話會先得到 `401`，看不到 `400` 或 `422`。

## 在瀏覽器裡看 API

`dotnet run --project src/OrderService.Api` 用的是 `Properties/launchSettings.json` 的 `http` 設定，環境是 `Development`。啟動後瀏覽器打開 `http://localhost:5064/swagger`。

這一頁是 Swagger UI，讀的是 `/openapi/v1.json`。那份 JSON 由 ASP.NET Core 內建的 OpenAPI 產生器寫出，內容是現有的路由、參數和 body。`Program.cs` 在 `Build()` 之後、例外 middleware 之前呼叫 `MapOrderServiceOpenApi()`，而且包在 `IsDevelopment()` 裡。換到別的環境，這個頁面和這份 JSON 都不會掛上。兩條都沒有 `RequireAuthorization()`，不帶 token 也能打開。

產生器看的是 `MapAuthEndpoints` 和 `MapOrderEndpoints`。`OpenApi/OpenApiExtensions.cs` 再補兩件事：

1. `BearerSecuritySchemeTransformer` 向容器確認有名為 Bearer 的驗證方案，然後在文件上宣告一種 HTTP Bearer，格式是 JWT。頁面右上角的 Authorize 就是這個方案。
2. `BearerSecurityRequirementTransformer` 看每一條路由的 metadata 有沒有 `IAuthorizeData`。`RequireAuthorization()` 會放上這筆 metadata，所以 `/orders` 底下的路由在頁面上帶鎖。`POST /register` 和 `POST /login` 沒有，頁面上不鎖。

在頁面上試一次：

1. 展開 `POST /register`，按 Try it out。body 用上一節的 `staff` / `practice`，再按 Execute。回應是 `201`。名稱已經註冊過就換一個，或直接做下一步。
2. 展開 `POST /login`，用同一組帳密。回應是 `200`，裡面有 `token`。
3. 按 Authorize，把 `token` 貼進去後確認。不要自己加 `Bearer` 前綴。頁面送出時會補上，和 curl 的 `Authorization: Bearer ...` 是同一個標頭。
4. 再對有鎖的 `POST /orders` 按 Execute。還沒 Authorize 就打，得到的是 `401`。

`EnablePersistAuthorization()` 讓這個分頁記住貼過的 token。token 過期，或 `SigningKey` 換過，要重新登入再貼一次。

文件描述路由和要不要帶 token。`400`、`422` 的欄位錯誤和業務規則仍以實際回應為準，看「輸入錯和業務規則錯」。

## 背景工作

`POST /orders` 只負責把訂單和一筆待辦一起存好，然後回 `201`。待辦的後續不放在這次請求裡，因為客戶端不需要等它，它失敗也不該把已經成立的訂單一起退掉。

`Program.cs` 註冊了 `OutboxWorker`。`app.Run()` 除了聽 `http://localhost:5064`，也會啟動它。它沒有網址。行程活著，它就查看 `outbox_messages` 裡 `processed_at_utc` 是空的列，一次最多 20 筆。沒有待辦，或這一輪有留下的，就等兩秒再看；這一輪全部成功就接著看後面的。每一筆依 `type` 交給對應的 handler。`OrderCreated`、`OrderPaid`、`OrderCancelled` 目前的 handler 都是在跑 API 的終端機印出 `Processed outbox message`，並帶上類型和訂單 id。印出來之後才把 `processed_at_utc` 寫上。handler 丟出例外，或 `type` 沒有對應的 handler，那一筆留著，下一輪再試。Ctrl+C 時宿主取消它的 `CancellationToken`，迴圈才離開。

這個 worker 是 Singleton，不能在建構式裡直接接 `AppDbContext`。每一輪它自己 `CreateAsyncScope()`，用完就釋放，下一輪再做一個。這一輪的 `OutboxDispatcher` 也從同一個 scope 取出。這和啟動時 `ApplyMigrationsAsync` 的寫法相同。

訂單狀態不會因為 worker 而改變。之後若有第二個服務要知道這些變化，換掉的是對應 `type` 的 handler。建立、付款、取消的請求還是先回結果。

## 自己看一次狀態變化

一個終端機留著 API，一個留著資料庫，第三個用來發請求。

```bash
docker-compose up -d
dotnet run --project src/OrderService.Api
```

API 位址是 `http://localhost:5064`。同一組請求也可以在 `http://localhost:5064/swagger` 上執行，步驟寫在「在瀏覽器裡看 API」。資料庫視窗：

```bash
docker-compose exec postgres psql -U postgres -d orderservice
```

建立訂單。`這裡換成token` 用上一節登入回應的 `token`：

```bash
curl -s -X POST http://localhost:5064/orders \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer 這裡換成token' \
  -d '{"customerName":"Ada","amount":120}'
```

跑 API 的終端機在兩秒內會印出 `Processed outbox message`，後面帶著這張訂單的 id。資料庫裡同一筆待辦的 `processed_at_utc` 已經有值：

```sql
SELECT type, payload, processed_at_utc FROM outbox_messages ORDER BY created_at_utc DESC;
```

用回傳的 id 查詢，這時 `status` 是 `Draft`：

```bash
curl -s http://localhost:5064/orders/這裡換成id \
  -H 'Authorization: Bearer 這裡換成token'
```

同一張 token 也可以列出自己的全部訂單：

```bash
curl -s http://localhost:5064/orders \
  -H 'Authorization: Bearer 這裡換成token'
```

改這張草稿的名稱和金額：

```bash
curl -s -X PUT http://localhost:5064/orders/這裡換成id \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer 這裡換成token' \
  -d '{"customerName":"Grace","amount":80}'
```

在 `psql` 看同一列：

```sql
SELECT id, customer_name, status FROM orders ORDER BY created_at_utc DESC;
```

付款：

```bash
curl -s -X POST http://localhost:5064/orders/這裡換成id/pay \
  -H 'Authorization: Bearer 這裡換成token'
```

回應和 `SELECT` 的 `status` 都會變成 `Paid`。跑 API 的終端機會印出對 `orders` 的 `UPDATE`，兩秒內也會印出 `Processed outbox message`，類型是 `OrderPaid`。

這張單再取消會失敗，HTTP 狀態是 `422`，資料庫仍是 `Paid`，也不會多一筆 `OrderCancelled`：

```bash
curl -i -X POST http://localhost:5064/orders/這裡換成id/cancel \
  -H 'Authorization: Bearer 這裡換成token'
```

要看取消成功，另建一張訂單，對那張打 `/cancel`。它會變成 `Cancelled`，並留下一筆 `OrderCancelled`。之後再打 `/pay` 會得到 `422`，狀態停在 `Cancelled`。已付款或已取消的訂單再 `PUT` 也是 `422`。

刪掉自己的一張訂單。成功沒有 body，狀態是 `204`；再用同一個 id 查詢會得到 `404`：

```bash
curl -i -X DELETE http://localhost:5064/orders/這裡換成id \
  -H 'Authorization: Bearer 這裡換成token'
```

## 輸入錯和業務規則錯

這兩種錯都是客戶端送來的資料有問題，但發生的位置不同。

輸入錯表示這份 JSON 還不能當成一筆建立訂單的命令。名稱空白、金額缺漏，由 `CreateOrderCommandValidator` 擋下。金額寫成文字時，ASP.NET Core 綁不上 `decimal?`，`Program.cs` 把這個綁定失敗轉成同一個 `400`，`errors.amount` 是 `Amount must be a number.`。這種回應的 `title` 是 `One or more validation errors occurred.`。

```bash
curl -i -X POST http://localhost:5064/orders \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer 這裡換成token' \
  -d '{"customerName":"","amount":10}'
```

```bash
curl -i -X POST http://localhost:5064/orders \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer 這裡換成token' \
  -d '{"customerName":"Ada","amount":"abc"}'
```

業務規則錯表示命令的形狀是對的，但 `Order` 不接受。金額 `0` 或 `-5` 是數字，名稱超過 200 字也是字串，這些會進到 `Order.Create`，再丟 `DomainException`。付款、取消的非法轉移也是同一種。回應是 `422`，`detail` 是那條規則的訊息。

```bash
curl -i -X POST http://localhost:5064/orders \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer 這裡換成token' \
  -d '{"customerName":"Ada","amount":0}'
```

`Order.Create` 仍會拒絕空白名稱和小於或等於 0 的金額。API 先做輸入檢查，領域方法繼續保護自己，避免以後別的進入點直接呼叫它。
